# Step-by-step integration plan

Each phase adds **one** tool, and you test it before moving on. Every phase lists
what to do, how to verify it, and what to say about it in the viva.
All settings live in `backend/.env`. Restart the backend after changing it
(with `--reload`, saving any `.py` file also restarts it).

| Phase | Adds | Extra RAM |
|---|---|---|
| 0 | Run backend + frontend | ~150 MB |
| 1 | System monitoring (psutil) | – |
| 2 | AI assistant (Gemini) | – (cloud) |
| 3 | Log analysis | – |
| 4 | Alerts + notifications | – |
| 5 | Docker monitoring | Docker Desktop |
| 6 | Containerise the dashboard (Docker Compose + Nginx) | ~200 MB |
| 7 | CI/CD: GitHub Actions, then Jenkins | Jenkins ~700 MB |
| 8 | Prometheus + node-exporter + Grafana | ~450 MB |
| 9 | Kubernetes (Minikube) | ~2.2 GB |
| 10 | Terraform + AWS | – (cloud) |

> **8 GB laptop tip (Windows):** Docker Desktop runs inside WSL2, which by default
> may take half your RAM. Create `C:\Users\<you>\.wslconfig` with
> ```
> [wsl2]
> memory=3GB
> processors=2
> ```
> then run `wsl --shutdown`. Stop components you are not demonstrating.

## Phase 0: Run the skeleton

```bash
cd backend
python -m venv venv
venv\Scripts\activate                 # Linux: source venv/bin/activate
pip install -r requirements.txt
copy .env.example .env                # Linux: cp .env.example .env
uvicorn app.main:app --reload --port 8000
```
```bash
cd frontend
npm install
npm run dev
```

**Verify**
- http://localhost:8000/api/health returns `{"status":"ok", ...}`
- http://localhost:8000/docs shows every endpoint (generated by FastAPI)
- http://localhost:5173 opens the Overview with your hostname and a live CPU/memory trace
- The **Tools** panel shows every integration as "Not set up yet". This is correct: nothing is faked.

**Explain:** React (Vite dev server) → `/api` proxy → FastAPI. In production Nginx does
the same proxying, so the frontend code never changes between environments.

## Phase 1: System monitoring (psutil)

Already active. Open **System**.

**Verify**
1. Watch the CPU gauge, then create load in another terminal:
   ```bash
   python -c "while True: pass"
   ```
   CPU rises within 5 seconds, and `python` appears at the top of **Top processes**.
   Stop it with Ctrl+C.
2. `curl http://localhost:8000/api/system/metrics` returns the same numbers as JSON.

**Explain:** a background task samples psutil every 5 s into a fixed-size ring buffer
(`collections.deque(maxlen=720)` = 1 hour). API calls read the latest sample, so
they are instant. The old code slept 1 s inside every request
(`cpu_percent(interval=1)`). The new code uses the non-blocking form.

## Phase 2: AI assistant (Google Gemini)

1. Create a free key: https://aistudio.google.com/apikey
2. In `backend/.env`: `GEMINI_API_KEY=your-key` (keep `GEMINI_MODEL=gemini-3.8-flash`).
3. Restart the backend.

**Verify**
- **AI assistant** → ask "Is anything on my system unhealthy right now?". The answer quotes your real CPU/memory numbers.
- Click **What is sent** to see the exact live data attached to the question.
- Turn **Use live data** off and ask a general question ("Explain Kubernetes Services").
- If you see "model not available", Google retired that model name. Set `GEMINI_MODEL` to a current one from https://ai.google.dev/gemini-api/docs/models. The backend also falls back to `GEMINI_FALLBACK_MODEL` automatically.

**Explain:** retrieval-augmented prompting (live context), secret redaction before
sending, smart log excerpts to stay within limits, model fallback. See VIVA_GUIDE.md §6.

## Phase 3: Log analysis

1. **Logs** → source *Dashboard backend* works immediately (it reads `backend/logs/app.log`).
2. **Operating system** source:
   - Windows: reads the System Event Log through `wevtutil` (built into Windows).
   - Linux: `journalctl` (your user may need: `sudo usermod -aG systemd-journal $USER`).
3. Add your own files (whitelist) in `.env`, for example:
   ```
   LOG_FILES=nginx=C:\nginx\logs\error.log;myapp=C:\projects\myapp\app.log
   ```

**Verify:** choose a source and filter by level. Click a level bar to filter. Search for text.
Click **Explain errors with AI**: only the warning/error lines are sent.

**Explain:** level detection (an explicit level field wins over words in the message),
grouping of repeated errors by masking numbers/IPs/IDs, reading only the end of large files,
and the whitelist that stops path traversal (`../../etc/passwd` is rejected).

## Phase 4: Alerts and notifications

1. For a quick demo, lower the CPU threshold in `.env`:
   ```
   ALERT_CPU_THRESHOLD=30
   ALERT_FOR_SAMPLES=3
   ```
2. Restart and run the CPU loop from Phase 1 for about 20 seconds.

**Verify**
- After 3 samples (about 15 s) a **High CPU usage** alert fires: the sidebar badge, the Alerts page, and a line in the backend log.
- Stop the load. The alert becomes **resolved** once CPU drops below threshold − 5 %.
- **Alerts → Turn on** browser pop-ups → **Send test notification**.
- Optional Slack/Discord: create an incoming webhook, then set `ALERT_WEBHOOK_URL` and
  `ALERT_WEBHOOK_FORMAT=slack` (or `discord`). The test notification arrives in the channel.
- Set the threshold back to 85 afterwards.

**Explain:** the state machine (pending → firing → resolved), the `for` window against
spikes, hysteresis against flapping, de-duplication by key, and SQLite persistence.

## Phase 5: Docker monitoring

1. Install Docker Desktop (Windows) or Docker Engine (Linux) and check that `docker ps` works.
2. `.env`: `DOCKER_ENABLED=true`, then restart.
3. Create one healthy and one crashing container:
   ```bash
   docker run -d --name demo-web -p 8090:80 nginx:alpine
   docker run --name demo-crash alpine sh -c "echo starting worker; echo ERROR could not connect to database at db:5432: Connection refused; exit 1"
   ```

**Verify**
- **Containers → Docker** lists both with CPU/memory. Restart/stop/start buttons work.
- Within 60 s an alert "Container demo-crash crashed (exit code 1)" fires.
- `demo-crash` → **Diagnose** → **Explain with AI** produces a root cause and fix.
- Clean up: `docker rm -f demo-web demo-crash`.

**Explain:** the CLI transport (laptop) vs the Engine API over the Unix socket (inside a
container), and the input validation that blocks option injection (`--help` as a name is rejected).

---

## Phase 6: Containerise the dashboard (Docker Compose + Nginx)

Stop the dev servers, then:
```bash
docker compose up -d --build
docker compose ps
```
**Verify:** http://localhost:8080 serves the dashboard through Nginx, and http://localhost:8080/api/health works.
The Docker page now shows `devops-backend` and `devops-frontend` themselves.

**Explain:** multi-stage builds (Node is not in the final image), non-root user,
HEALTHCHECK, Nginx reverse proxy (one origin, so no CORS), memory limits, named volumes.
Note: inside a container psutil measures the **container's** view. For laptop
metrics, use dev mode or node-exporter (Phase 8).

## Phase 7: CI/CD

### 7a. GitHub Actions
1. Create a GitHub repository and push this project. `.github/workflows/ci.yml` runs automatically.
2. Create a fine-grained token: GitHub → Settings → Developer settings → Fine-grained tokens →
   this repository → *Actions: Read and write*, *Contents: Read*.
3. `.env`:
   ```
   GITHUB_REPOS=your-user/devops-ai-dashboard
   GITHUB_TOKEN=github_pat_...
   ```

**Verify:** **Pipelines** lists the runs. Expand a run to see its jobs and steps.
Then break a test on purpose (for example, change an expected value in
`backend/tests/test_units.py`), commit and push. The run fails, a "Workflow failed"
alert fires, and **Diagnose** explains the failing pytest output. Revert, push, and the alert resolves.

### 7b. Jenkins
Follow `jenkins/README.md`:
```bash
docker compose --profile ci up -d --build jenkins
```
Create the pipeline job from `Jenkinsfile`, create an API token, and set `JENKINS_URL`,
`JENKINS_USER` and `JENKINS_TOKEN`.

**Verify:** the job appears on **Pipelines**. **Build** queues a real build. A failed build
gets **Diagnose**. Stop Jenkins after the demo: `docker compose stop jenkins`.

**Explain:** pipeline stages, tests running inside a Docker build stage (Jenkins needs no
Python/Node), and deploy + smoke test only on `main`.

## Phase 8: Prometheus, node-exporter and Grafana

```bash
docker compose --profile monitoring up -d
```
`.env` (when the backend runs on your laptop in dev mode):
```
PROMETHEUS_URL=http://localhost:9090
GRAFANA_URL=http://localhost:3000
```
If the backend runs **in compose** (Phase 6), put the URLs in a root `.env` file next to
`docker-compose.yml` instead (copy `.env.example`) and run `docker compose up -d` again:
```
PROMETHEUS_URL=http://prometheus:9090
GRAFANA_URL=http://localhost:3000
```
If the backend runs in dev mode (not in compose), tell Prometheus where it is: in
`monitoring/prometheus/prometheus.yml` change `backend:8000` to `host.docker.internal:8000`, then
```bash
curl -X POST http://localhost:9090/-/reload
```

**Verify**
- http://localhost:9090/targets shows all jobs **UP**.
- **Infrastructure** → presets draw real charts. Try a custom query: `up`.
- **Open Grafana** → *DevOps AI Overview* dashboard (provisioned automatically; login admin/admin).
- Stop node-exporter (`docker compose stop node-exporter`). After 1–2 minutes the `TargetDown`
  rule fires and appears on the Alerts page. Start it again.

**Explain:** the pull model, PromQL, recording our own `/metrics` with `prometheus_client`,
label cardinality, provisioning as code, and retention limited to 3 days to save disk.
On Windows, node-exporter measures the Docker VM. For real Windows host metrics install
`windows_exporter` and uncomment the `windows-host` job.

## Phase 9: Kubernetes (Minikube)

```bash
minikube start --memory=2200 --cpus=2
minikube addons enable metrics-server
kubectl get pods -A
```
`.env`: `KUBERNETES_ENABLED=true`, then restart.

Create a healthy and a broken workload:
```bash
kubectl create deployment hello --image=nginx:alpine
kubectl create deployment broken --image=busybox -- sh -c "echo starting; echo FATAL missing env DATABASE_URL; exit 1"
```

**Verify**
- **Containers → Kubernetes** shows the node, pods, deployments, services and warning events.
- `broken` goes into **CrashLoopBackOff**, a critical alert fires, and **Diagnose** explains it.
- **Restart** on a deployment performs a real `kubectl rollout restart`.
- Clean up: `kubectl delete deployment hello broken`.

**Bonus: deploy the dashboard into the cluster** (see `k8s/README.md`). Inside the cluster it
switches to "in-cluster" mode and authenticates with its ServiceAccount (read-only RBAC).

---

## Phase 10: Terraform + AWS

Follow `terraform/README.md`: `terraform init` → `plan` → `apply` creates the EC2 instance, IAM role,
S3 bucket, SSM secret and CloudWatch alarms, and the instance installs and starts the dashboard by itself.

For the dashboard's AWS panel from your laptop:
```bash
pip install -r requirements-aws.txt
aws configure            # an IAM user with ReadOnlyAccess is enough
```
`.env`: `AWS_ENABLED=true`, `AWS_REGION=ap-south-1`.

**Verify:** **Infrastructure → AWS** lists EC2 instances with CloudWatch CPU, S3 buckets and alarms.
**Always run `terraform destroy` after the demo** to avoid charges.
